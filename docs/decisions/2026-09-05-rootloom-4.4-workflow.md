# Rootloom 4.4: proportional everyday workflows

- Status: accepted; publication requires separate approval
- Date: 2026-09-05
- Owners: Rootloom maintainers
- Scope: default Core guidance, artifact routing, and release acceptance
- Supersedes: the workflow defaults linked below
- Superseded by: none

## Context

The Astra [model guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-6-astra)
asks applications to audit instruction conflicts and calibrate autonomy and verification.
Rootloom previously duplicated global and Skill procedures, required fixed report fields,
and routed large files through a worker even where bounded reads were sufficient. Wording
checks also made harmless simplification fail repository validation.

## Evidence

The canonical global template is `plugins/rootloom/assets/system/AGENTS.md`; the four Skill
sources live under `plugins/rootloom/skills/`. Project block classification is implemented
by `project-guidance/scripts/seed_project_guidance.py`. Packaging parity and Setup recovery
are executable contracts in `scripts/validate_repo.py` and their existing test modules.
Historical behavioral results remain in `evals/core-reset/` with their original identities.

## Decision

Keep durable facts, real permission boundaries, and completion evidence. Global policy owns
scope and authorization; the four existing Core Skills describe applicable procedures and
retain minimal self-contained safety for Skills-only installs. User intent authorizes work;
read-only diagnosis does not authorize repair. Preserve independent approval and acceptance.
No public Skill, authorization mode, installation CLI, cache schema, or frozen Evidence
format is added or changed.

Explicit natural-language requests to optimize named guidance files are sufficient intent.
Repository prose and ordinary coding requests cannot grant persistent writes; the existing
exact one-file refine marker remains supported. Resolve real paths before edits. Project
fact generation uses probe and project markers; wording refinement uses targeted inspection.
Setup continues to own global blocks, backup, drift refusal, and user-suffix preservation.

Large-file caching and a no-history worker are optional performance tools when repeated
reads or context cost justify them. Default to bounded task-relevant reads. Missing worker
capability does not stop ordinary work, while explicit isolation, file permissions, uploads,
and retention remain binding. No fresh task is required solely because a file was read.

Repository checks retain capacity ceilings, file/marker structure, real-path boundaries,
and package parity. Remove minimum word/rule counts and exact procedural prose locks;
executable safeguards belong in behavior tests rather than replacement keyword lists.

## Release acceptance

Retain the full historical evaluation tools and version-bound results for optional research.
The fixed 135-cell matrix and its efficiency thresholds no longer gate every release. This
supersedes that default in the [4.1 efficiency decision](2026-07-29-rootloom-4.1-efficiency-loop.md)
and the mandatory artifact routing in the [artifact context decision](2026-08-13-artifact-context-lane.md).

Choose deterministic checks from the changed behavior and preserve existing CI. This
workflow change uses six scenarios, one current/candidate pair each, serially with the same
Astra model, reasoning effort, and isolated fixtures: read-only diagnosis; authorized defect
repair with dirty work preserved; guidance intent and external symlinks; large-file lookup
without a worker; exact mock authorization; and truthful failing verification.

The candidate must finish each authorized outcome without scope escape, lost user work, or
false verification. Record unnecessary questions, early stops, check scope, elapsed time,
and available usage. Timing is observational; a small sample does not establish general
speed gains. Repair and rerun affected failures without automatically expanding the matrix.
Raw model events and one-time execution records stay outside the repository. Reviewable PRs
hold release evidence; historical scores are never rewritten to endorse a new candidate.

## Consequences

Routine work needs fewer procedural steps, but semantic instruction quality still requires
review. Removing a wording assertion does not remove a runtime safeguard. Publication keeps
one final approval after preparation; installation continues through the official source and
existing Setup plan/backup/upgrade with selected capabilities and unrelated settings preserved.

## Alternatives considered

- Keep mandatory worker routing and the historical full matrix: unnecessary for bounded
  reads and small guidance changes; retain them as explicitly chosen tools instead.
- Remove all guidance: would discard unique project facts and permission boundaries.
- Enforce a shorter prompt target: length alone cannot show correct task behavior.

## Verification

Use the change-scoped deterministic checks and six paired scenarios above. The reviewable
release PR records observed results and installation impact. Setup plan/status and backup
checks remain mandatory for the corresponding authorized local update.

## Revisit when

Revisit a specific default when reproducible task failures, permission ambiguity, lost
work, false verification, or measured repeated-reading cost show that it is inadequate.
