# 默认使用影响范围内的精准验证

- 状态：accepted
- 日期：2026-08-10
- 负责人：Rootloom maintainers
- 范围：可安装验证治理与 Rootloom 仓库 CI
- 取代：none
- 被取代：none

## 背景

Rootloom 原本要求验证与影响成比例，却没有定义何时才有理由扩大回归范围。仓库因此在
四个 Linux Python 版本上重复完整单元套件，又在 macOS 和 Windows 各重复一次。模型
也可能把回滚、宽泛风险提示，或现成的测试命令误解成“所有修改都要全量验证”，即使
变更归属与消费者已经可以明确界定。

修正必须减少重复工作，同时不能让未知可执行变更静默通过。方案必须能直接从仓库源码
审查，不能新增依赖图服务、历史测试数据库或另一种持久格式。

## 决策

Rootloom 治理和本仓库都默认使用影响范围内的精准验证：

1. 按变更归属、已知消费者和一条相邻行为路径选择检查。每个平台或运行时 Lane 都必须
   证明一种独立风险。
2. `scripts/impact_tests.py` 拥有静态、可审查的路径到组件映射。已知纯文档变更只运行
   结构校验；未知可执行路径，以及选择器、校验器、Makefile 或 CI Workflow 自身变化，
   都失败关闭到全量套件。
3. Pull Request 运行精准测试。`main` 在 Python 3.11 保留一次规范性全量套件；
   Python 3.14 和 macOS/Windows 按组件选择 `COMPATIBILITY_TESTS` 中的具名兼容场景，
   每项说明其运行时或操作系统风险。主通道保留受影响模块的全部断言；未知或共享变更
   选择主通道全量套件和全部具名兼容场景。仓库校验拒绝缺失分组、失效名称、重复项和
   错误的组件归属。定时或手动运行覆盖完整支持 Python
   矩阵与完整可移植契约子集。
4. 固定 Codex 安装冒烟只在安装或包加载路径变化时运行。每周 latest-Codex 探针先校验
   结构，再验证 CLI 兼容边界，不重复无关单元测试。
5. 当影响无法界定，或明确仓库/发布契约要求时，仍可运行全量套件或矩阵。全量命令的
   存在、回滚价值或执行方便本身都不是触发条件。

## 考虑过的替代方案

- 保留日常六次全量套件——拒绝，因为其中五次重复未受影响行为，不能证明独立的平台
  或版本风险。
- 根据覆盖率或测试历史建立动态依赖图——拒绝，因为它的维护与失效成本超过当前仓库
  规模和需求。
- 只运行精准测试且不设置回退——拒绝，因为新可执行路径可能在补充映射前被漏掉。

## 后果

- 正面：日常修改更快获得与真实归属和消费者对应的证据。
- 正面：未知或共享测试选择变更仍通过显式全量回退保持保守。
- 负面：新增可执行组件或测试归属时，必须更新静态映射。
- 取舍：日常附加环境抽查集成边界，不重复每种策略或 Schema 组合；定时全矩阵继续
  提供更广覆盖。
- 运维：本地分支比较包含受跟踪的工作树变更，默认排除无关未跟踪文件；纳入未跟踪文件
  必须显式指定。
- 运维：现有安装在正常升级 Rootloom 时采用新治理措辞；回滚恢复完整旧版本。不改变
  Wire Format、持久数据或运行时兼容路径。

## 验证

- `tests/test_impact_tests.py` 证明纯文档选择、组件映射、平台/Codex Flag 和失败关闭回退。
- `tests/test_core_reset_eval.py` 证明全局治理、Change Skill 与验证 Reference 保持相同
  默认值和停止条件。
- `scripts/validate_repo.py` 把选择器、CI 拓扑、Make Target、治理措辞、中英文文档和
  本决策绑定进仓库校验。

## 重新评估条件

- 组件边界增长到静态映射难以审查。
- CI 失败数据表明某个被省略的平台/运行时 Lane 本可捕获相关缺陷，或某个已选 Lane
  持续不能证明独立风险。
- 仓库采用权威依赖图，而且它比静态映射更简单并至少同样失败关闭。
