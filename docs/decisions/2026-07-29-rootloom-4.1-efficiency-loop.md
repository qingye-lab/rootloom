# Make Rootloom Core efficiency measurable and route-aware

- Status: accepted
- Date: 2026-07-29
- Owners: Rootloom maintainers
- Scope: Change mode routing, Core Reset evaluation, deterministic Evidence orchestration, and SessionStart command rendering
- Supersedes: none
- Superseded by: none

## Context

The 4.0 Core Reset proved that four public Skills can preserve the tested 3.4 task
outcomes, but its retained behavioral matrix had one execution per cell and its
elapsed-time margin was only 0.11%. It also measured prompt bytes rather than the
actual token accounting emitted by Codex, did not score exact Reference routes, and
did not cover Project Guidance or Setup. The 4.0 Change wording allowed routine
models to over-inspect a dirty worktree, and strict Evidence required several low-level
commands even for the common intake → edit → finalize path.

The correction must improve the operating loop without changing the frozen Baseline v2–v4,
Summary revision 5, contract, review-manifest, or seal formats. It must not
promote optional Autonomy or experimental Memory into the default path.

## Decision

Rootloom 4.1 adopts an efficiency loop with six owning rules:

1. Core Reset v2 compares No Rootloom, 3.4, and 4.1 with real `turn.completed` token
   fields, command/message counts, exact Skill/Reference routing, deterministic task
   randomization, and isolated per-run Codex homes.
2. A formal candidate result requires at least three repetitions per scenario/variant
   cell through `make core-reset-release-eval CORE_RESET_RESULTS=/absolute/result.json`.
   A structural run remains useful during implementation but is not behavioral release
   proof.
3. Routine Change is self-contained. Direct and Scoped load no Reference: Direct stays
   on the exact target and smallest relevant check, while Scoped keeps proportional
   evidence, behavior-mapped verification, and one post-check challenge in the main
   Skill. Independent reads and final state inspection are batched when practical so
   narration or commands that cannot change the next decision do not create another
   model/tool round. A dirty worktree alone does not escalate the mode. An initially
   unknown defect cause stays in bounded Scoped diagnosis; only material root-cause
   uncertainty that remains after diagnosis is a Governed signal.
4. `orchestrate_evidence.py prepare` and `finish` compose the existing intake, exact
   contract replacement, seal, and finalizer CLIs. They do not add a format or relax
   strict verification; `finish` requires an explicit semantic-review assertion. The
   orchestrator is a one-verification-command convenience path, while heterogeneous
   commands, targets, components, migrations, security, or mixed-version evidence use
   the low-level lifecycle.
5. SessionStart only renders package-script names from a conservative safe identifier
   set. Unsafe names are ignored rather than sanitized into suggested commands.
6. Repository guidance may request read-only validation automatically. Persistent seed,
   refresh, or refinement requires explicit user intent; one file may alternatively
   request one refinement through the exact standalone
   `<!-- rootloom:refine-once version=1 -->` marker, consumed by the successful write.

The v2 suite adds Guidance seed/validate and Setup plan/round-trip scenarios. It keeps
the historical v1 suite and 4.0 result as historical evidence rather than rewriting or
rebinding them to a new Core tree.

## Alternatives considered

- Treat 4.0's one-run elapsed result as sufficient for 4.1 — rejected because its
  margin does not distinguish product change from run variance.
- Add a new Evidence bundle or Summary revision for orchestration — rejected because
  the orchestration is workflow ergonomics, not a new persisted contract.
- Make Autonomy or Memory part of every 4.1 run — rejected because the Core Reset
  boundary explicitly keeps both optional and their effects need a separate decision.
- Escape all package-script names for display — rejected because the renderer is meant
  to offer executable suggestions; omission is more reliable than preserving an
  ambiguous shell-like string.

## Consequences

- Positive: route overreach and underreach become measurable regressions rather than
  qualitative impressions.
- Positive: release evidence uses actual token accounting and repeated comparisons.
- Positive: common strict Evidence work has two high-level lifecycle commands while
  advanced low-level controls remain available.
- Positive: initial diagnostic uncertainty no longer over-routes ordinary defects, and
  natural-language repository prose cannot silently authorize persistent guidance edits.
- Positive: Scoped changes no longer pay a second Skill-loading round while retaining
  the same verification and challenge obligations.
- Negative: formal evaluation costs more model turns and is deliberately not run by
  ordinary repository checks.
- Negative: uncommon package-script naming conventions outside the safe identifier set
  will not appear in temporary guidance until a separate safe-rendering decision.
- Operational: a 4.1 implementation is not a formal behavioral release acceptance
  until a v2 three-repetition result is captured, scored, reviewed, and bound to the
  final plugin tree digest.

## Verification

- `tests/test_core_reset_eval.py` checks v2 result validation, three-repetition gates,
  current-tree binding, route failures, bounded root-cause escalation, Guidance write
  authorization, and the orchestrator convenience boundary.
- `tests/test_evidence_orchestrator.py` proves prepare/seal/finalize against the
  existing strict wire formats.
- `tests/test_seed_project_guidance.py` proves unsafe script keys do not enter Hook
  context while a normal `test:unit` key remains available.
- `make core-reset-release-eval` rejects missing results and requires three repetitions;
  a formal result must pass it with the final candidate digest.

## Revisit when

- Three-repetition results show no route, token, command-count, or elapsed-time benefit
  without a quality tradeoff.
- Codex changes the event usage schema or private Skill-routing behavior.
- Safe package-script display can be shown to preserve a broader set of names without
  producing command-like untrusted text.
- Autonomy or Memory has separate product evidence sufficient to justify changing the
  Core default boundary.
